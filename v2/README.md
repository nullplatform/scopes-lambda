# lambda-v2: AWS Lambda as an engine scope

The `lambda` scope re-implemented on nullplatform's scope orchestrator: a Pulumi program the platform
runs for every lifecycle transition, with provider calls executed by a slim worker in your
infrastructure. No credential ever reaches nullplatform; the worker resolves them next to the `aws`
provider.

- `src/program.ts` — the program. Declared once; `create-scope`, `start-initial`, `start-blue-green`,
  `switch-traffic`, `finalize`, `rollback`, `update-scope` and `delete-scope` are the same program with
  different `releases`.
- `src/resources.ts` — the scope type: the legacy attributes schema byte for byte (`src/schema.ts`,
  generated by `scripts/legacy-schema.py`), plus read-only outputs the program records.
- `src/actions/` — the telemetry data actions answered by the package: `log:read`, `metric:list`,
  `metric:read`.
- `Dockerfile` + `providers.json` — the worker image: the scope provider host plus `aws@7.2.0`.

## What the program declares

| Part | Resources | Legacy name kept |
|---|---|---|
| Execution role | `aws.iam.Role` + the policies `scope-configurations.lambda.role_policies` lists (+ DLQ, VPC) | `<prefix><function>-role` |
| Log group | `aws.cloudwatch.LogGroup` | `/aws/lambda/<function>` |
| Function | `aws.lambda.Function` (`publish: true`), image or zip, placeholder before the first release | `<scopeId>-<app>-<scope>` (64 chars) |
| Releases | one published version per release, read back from the stack's own `release_versions` output | — |
| Alias `main` | points at the active release; `routingConfig` carries the candidate's weight | `main` |
| Concurrency | reserved on the function, provisioned on the alias (and a `warmup` alias when asked) | — |
| Parameters | `env`: each parameter as an environment variable (`$npSecret` reference, resolved on the worker); `secretsmanager`: one secret per release | `nullplatform/<scope>/<deployment>/parameters` |
| Invoke permissions | `aws.lambda.Permission` per `scope-configurations.triggers.invoke_permissions` entry | — |
| HTTP | ALB target group + listener rule (`visibility` picks the listener) or API Gateway HTTP API | `<ns>-<app>-<scope>` |
| DNS | Route53 CNAME on the account's hosted zone | `<ns>-<app>-<scope>.<zone>` |

Before the first deployment the alias serves `$LATEST`, the placeholder: the configured
`placeholder_image_uri` (ECR) for image scopes, an inline handler for zip ones (on the scope's own
runtime when it is a Node one).

## Provider keys the program reads

| Category | Keys |
|---|---|
| `cloud-providers` | `account.id`, `account.region`, `networking.hosted_public_zone_id`, `networking.hosted_zone_id` |
| `vpc` | `vpc.id`, `vpc.subnets`, `vpc.security_groups`, `load_balancer.public.listener_arn`, `load_balancer.private.listener_arn` |
| `scope-configurations` | `deployment.placeholder_image_uri`, `deployment.parameters_strategy` (`env`, default, or `secretsmanager`), `lambda.execution_role_prefix`, `lambda.permissions_boundary`, `lambda.role_policies[]`, `triggers.invoke_permissions[]`, `agent.null_agent_layer_arn` |

The worker's `platform` credential profile reads `cloud-providers.region` and
`aws-iam-configuration.arns.lambda` (the role it assumes) for the provider; the data actions use the
same two lookups.

## Secret references

The program never sees a parameter value. It writes `{"$npSecret": "np://parameter/<id>"}` (env
strategy) or `{"$npSecret": "np://parameters/<deploymentId>"}` (the JSON of every parameter value at
the scope, for the Secrets Manager secret) and the worker resolves them right before the provider call.
What the provider echoes back is restored to the reference or redacted before it reaches the state.

## Develop

```bash
bun install
bun test                       # schema, describe, data actions, image manifest
npm run test:program           # the program under Node with Pulumi mocks
bun run build:program          # dist/program: what `np package publish` ships
docker build --build-arg PROVIDER_HOST_IMAGE=scope-provider-host:<version> -t scopes-lambda-v2 .
```

The orchestrator's `test/functional/programs/lambda-v2.spec.js` runs this scope end to end against
LocalStack (`LAMBDA_V2_DIR=<this directory> LOCALSTACK_URL=... npm run test:functional` there).

## Publish

```bash
np package publish --program-bundle   # builds the bundle, pushes it as an OCI artifact, registers the package
```

## Differences from the legacy scope

- Old published versions are not deleted on finalize or rollback; AWS keeps them until pruned.
- The listener rule priority is derived from the scope id (`100 + hash % 50000`) instead of a shared
  constant.
- DNS is a CNAME to the load balancer or API endpoint (the legacy alias record needed an API custom
  domain no workflow created).
- `diagnose-*`, `invoke` and `adjust-*-concurrency` are not carried over yet.
